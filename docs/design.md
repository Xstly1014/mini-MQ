# mini-MQ 设计文档 · M0 —— 立项调研与存储内核决策

> M0 任务 1 交付物（对应 Spec m0t1）。本文记录对比 Kafka / RocketMQ / Pulsar 后的裁剪决策、
> v0 消息格式与写入路径定稿。M0 的三条硬验收：CommitLog 裸写吞吐 ≥ 5 万 msg/s @1KB（NVMe 参考量级）、
> CRC 截断行为有单测、本决策表成文。重大决策的完整 ADR 档案在 M6 收口（docs/adr/）。

## 1. 调研方法与三家差异

调研不列功能清单，只问三个问题：**数据写到哪几个文件？读的时候怎么定位？挂了怎么恢复？**——三家的答案差异就是架构差异。

| 维度 | Kafka | RocketMQ | Pulsar |
|------|-------|----------|--------|
| 存储模型 | 分区日志：每个 Partition 一组独立追加写文件（LogSegment） | **全局单 CommitLog**：所有 Topic 混写同一顺序文件 + ConsumeQueue 异步索引 | 存算分离：Broker 无状态，数据写入 BookKeeper 的 ledger 分片 |
| 写入路径 | 1000 个 Partition = 1000 个文件同时写 → **随机 IO 化风险**（页缓存可掩盖，堆积超出内存后暴露） | 无论多少 Topic，永远只有**一条顺序写流**——以不变应万变 | 写入多一跳网络（Broker → Bookie），延迟高但弹性最好 |
| 消费定位 | offset 直接定位分区文件，简单直接 | ConsumeQueue 只存物理位置（8B offset + 4B size），随机读优异 | ledger 分片天然散布，扩缩容不搬数据 |
| 复杂度 | 单机最简 | 中等（CommitLog + ConsumeQueue + IndexFile 三层） | 最高（Broker + BookKeeper 两套系统） |

调研中确认的 Kafka 已知短板（不是看广告）：多 Partition 并发写导致块设备随机 IO 化；分区数不可缩减；元数据随分区数线性膨胀。

## 2. 裁剪决策表（抄谁、裁谁、为什么）

| # | 决策点 | 结论 | 理由（问题驱动） | 否决的备选 |
|---|--------|------|------------------|-----------|
| D1 | 存储模型 | **抄 RocketMQ：全局单 CommitLog** | v0 单 topic 起步，单文件顺序写是最容易做对的形态；"多 topic 混写单文件"正是 RocketMQ 对 Kafka 多分区随机 IO 化的核心改进——抄它等于站在它的架构判断上 | Kafka 分区文件（v0 无多分区需求，白担随机 IO 风险）；Pulsar 分层（见 D5） |
| D2 | 索引 | **v0 不做 ConsumeQueue，顺序遍历定位** | 单 topic 顺序消费暂时可以遍历文件；M1 网络层接入后再补稀疏索引——先立吞吐基线再演进，避免一次设计到位的过度工程 | 一次到位做三层存储（ConsumeQueue + IndexFile） |
| D3 | 复制协议 | **抄 Kafka：fetch 同步 + Leader Epoch + HW**（M3 实施，此处定调） | 消息队列数据面本就不是 Raft：多分区高吞吐下全序日志是序列化瓶颈；epoch + HW 用更轻的机制达到等价的脑裂防护与不丢保证。KIP-500/KRaft 自己也只在元数据层用 Raft，数据面保持 fetch 复制 | 全链路 Raft（写放大模型不匹配） |
| D4 | 选举 | **只取 Raft 的选举内核**（term/多数派/随机超时/PreVote，M3） | 选举正确性问题（防双投/防脑裂/防选举风暴）Raft 有最完整的工程答案；只借选举不借日志复制，与 D3 组成 KRaft 同款混合架构 | ZK 式外部协调（另一个学习成本黑洞）；老版 Kafka 的 ZK Controller 选举 |
| D5 | 明确不抄 | **Pulsar 的存算分离** | 同时实现 Broker + BookKeeper 两个系统（ledger/ensemble/quorum 三参数组）对个人项目是复杂度黑洞；其收益（多租户/跨地域/弹性）在 3 节点规模下无法兑现——"知道它好但明确不做"本身是裁剪能力 | —— |
| D6 | 元数据/协调 | **无 ZK：静态拓扑 + 心跳租约** | 3 节点元数据量极小，静态配置足够；已知失效边界约在 10 节点级（动态成员变更才需要共识协商），写明边界是诚实的工程判断 | ZK / KRaft 全套元数据管理 |

一句话总结：**存储学 RocketMQ，复制学 Kafka，选举学 Raft，Pulsar 明确不学**——每个子系统各拜一个师傅，且都能说清为什么。

## 3. 消息格式（v1.1，M1 起）

```
┌────────────┬───────┬──────┬───────────┬────────┬───────────┬─────────────┬───────┬─────────┐
│ TOTAL_SIZE │ MAGIC │ CRC  │ TIMESTAMP │ KEYHASH│ TOPIC_LEN │ PAYLOAD_LEN │ TOPIC │ PAYLOAD │
│    4B      │  1B   │  4B  │    8B     │   8B   │    2B     │     4B      │  nB   │   mB    │
└────────────┴───────┴──────┴───────────┴────────┴───────────┴─────────────┴───────┴─────────┘
```

- 全字段**小端序**（x86 亲和）。注意：M1 的网络帧协议采用大端序（网络行业惯例）——两层各自约定、绝不混用，此差异已写入 M1 手册的"字节序陷阱"。
- **TOTAL_SIZE** = 31 + topicLen + payloadLen，是恢复扫描的"跳板"：坏一条消息靠 size 直接定位边界，而不是全盘报废——破损容忍的前提。
- **MAGIC**（0x6E）：消息格式版本位。v1.0（M0，29B 头无 TOPIC）用 0x6D；v1.1 加入 TOPIC 时 bump——两种布局永远不可能被混淆，这就是版本位存在的意义本身。
- **CRC32**：两段式覆盖 MAGIC + [TIMESTAMP .. 记录末尾]（避开 CRC 字段自身）；断电写一半的消息校验失败即截断（对齐 RocketMQ 行为）。
- **TIMESTAMP**：消息时间，TTL/延迟诊断的存储基础。
- **KEYHASH**：幂等键 hash，M4 生产端去重窗口的占位——现在就留字段，避免格式破坏性升级。
- **TOPIC**（v1.1 新增）：UTF-8 变长，上限 1KB。M1 网络层的 PRODUCE/FETCH 按 topic 路由；在 ConsumeQueue（M2）落地前，消费侧按 topic 顺序扫描过滤。

**演进记录**：v1.0 → v1.1 在无存量数据的窗口期完成（M0 刚验收即改，成本最低）；若在有存量数据的系统上做此演进，需要双版本读路径 + 逐段迁移——这正是"协议/格式定了就难改"的实证，也是把 topic 字段决策提前到 M1 的原因。

## 4. 写入路径：mmap（含边界认知）

| 路径 | 内核过程 | 结论 |
|------|----------|------|
| FileChannel.write(HeapBuffer) | JDK 先把堆内 buffer 拷贝到临时 DirectBuffer（GC 会移动对象，系统调用必须用堆外地址）→ write() → page cache；每次写都切内核态 | 能用，但每次写都有隐藏拷贝 + 系统调用成本 |
| fileChannel.map() → MappedByteBuffer | 映射建立后写 buffer = 直接写 page cache，无中转、无逐次系统调用 | 高频小块写（消息负载）的最优解，RocketMQ 的选择 |

**必须知道的边界**（面试防坑，也是 v0 实现约束）：
1. mmap + write **不是严格零拷贝**——page cache → socket 仍有一次 CPU 拷贝与上下文切换；严格零拷贝要等 M2 的 sendfile（消费路径 transferTo）。
2. Java 无公开 unmap API，MappedByteBuffer 释放靠 GC/Cleaner——所以只常驻"当前段 + 恢复段"少量映射（1GB × 个位数），已完成段读旧数据时按需临时映射。
3. Windows 下被映射的文件删除受限——开发期接受（进程退出即释放）；测试数据目录放在 target/ 下不做删除。

## 5. 文件段设计与恢复语义

- **1GB 预分配段 + 滚动**：建段时一次性 setLength 到 1GB（写路径上不做慢动作）；文件名 = 段起始全局 offset（20 位十进制零填充）——文件名即索引。
- **恢复只扫最后一段，O(尾段) 不是 O(全量)**：逐条校验 size/magic/CRC，坏点即截断至 lastValidOffset。段切换的"提前预分配下一段 + 预热（每 4KB 写 0 防缺页中断）"留到 M2 压测实证卡顿后再补——一次实证胜过十篇博客。
- **非末段按满段处理的假设**：滚动仅在当前段写满时触发，故非末段必然是满的（不变量由构造保证）；若该不变量被破坏（手工删段/改文件），打开时按段链连续性校验直接报错。
- **截断语义**：恢复只回退 wrotePosition，不物理清零坏区——后续读以 wrotePosition 为边界，坏区对新写入而言会被自然覆盖。

## 6. M0 基准设计（四模式，结果见 docs/bench-v0.md）

| 模式 | 回答的问题 | 预期量级（NVMe 参考） |
|------|-----------|----------------------|
| A. mmap 纯写（不 force） | page cache 吞吐上限——异步刷盘模式的能力边界 | 数十万 msg/s @1KB |
| B. mmap + 每条 force | 最坏情况——"每条都落盘"有多贵 | 暴跌约两个数量级 |
| C. mmap + 每 N 条 force | **组提交的立项依据**——B 和 A 之间能拿回多少 | N=64 时接近 A 的 60%+ |
| D. FileChannel + DirectBuffer | mmap 增益是否真实可测（第 4 节决策的验证） | 略低于 A |

A 与 B 的巨大差距 = M2 组提交的全部"预算证明"（Kafka linger.ms / RocketMQ 组提交线程 / MySQL redo 批量刷盘都在做同一件事）。A 模式数字是 page cache 吞吐不是持久化吞吐——掉电丢未刷盘脏页，这正是 M3 副本与 M4 三段防线的存在意义。

## 7. v0 边界承诺（明确不做）

事务消息、跨机房、rebalance 完整协议、安全认证、多分区（v0 单 topic）、ConsumeQueue 三层索引——每一条的裁剪理由见上表与 M6 的 ADR 档案。目标不是生产可用，是**核心机制正确 + 可量化**。
